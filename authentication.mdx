Каждый запрос к API V3 Custody должен быть аутентифицирован. Платформа построена на better‑auth и принимает два способа: **Bearer‑токен** (для серверных интеграций и мобильных приложений) и **httpOnly‑cookie** (для веб‑консоли). Любой эндпоинт понимает оба.

<Callout kind="alert" collapsed="false">
  Токен - это доступ к средствам и операциям. Не коммитьте его в репозиторий и не встраивайте в код: храните в переменных окружения или менеджере секретов.
</Callout>

## Два способа аутентификации

### Bearer - сервисы и мобильные приложения

Передайте токен сессии better‑auth в заголовке `Authorization`. Так аутентифицируются серверные интеграции и мобильные клиенты.

<ParamField header="Authorization" param-type="string" required="true" deprecated="false" show-location="true">
  Bearer‑токен: `Authorization: Bearer <токен>`.
</ParamField>

<CodeGroup show-lines="true">
  ```bash
  curl "[BASE_URL]/api/v1/vaults" \
    -H "Authorization: Bearer $V3_TOKEN"
  ```

  ```javascript
  const res = await fetch("[BASE_URL]/api/v1/vaults", {
    headers: { Authorization: `Bearer ${process.env.V3_TOKEN}` },
  });
  ```

  ```python
  import os, requests

  res = requests.get(
      "[BASE_URL]/api/v1/vaults",
      headers={"Authorization": f"Bearer {os.environ['V3_TOKEN']}"},
  )
  ```
</CodeGroup>

### Cookie - веб‑консоль

При входе в веб‑консоль better‑auth выставляет httpOnly‑cookie с сессией. Браузер отправляет её автоматически, вручную с ней работать не нужно, а из JavaScript она недоступна по замыслу. Для интеграций «сервер↔сервер» используйте Bearer‑токен, а не cookie.

## Регистрация только по приглашению

Самостоятельная регистрация закрыта: hook better‑auth блокирует sign‑up без действующего приглашения. Новый участник попадает в Vault так:

<Steps>
  <Step title="Администратор создаёт приглашение" icon="mail" title-type="p">
    Указываются email и список групп, в которые участник попадёт при принятии. Эндпоинт - `POST /api/v1/invitations`.
  </Step>

  <Step title="Участник принимает приглашение" icon="user-check" title-type="p">
    При регистрации по приглашению better‑auth автоматически создаёт членства в группах (`PolicyGroupMembership`) и помечает приглашение принятым.
  </Step>

  <Step title="Доступ определяется группами" icon="users" title-type="p">
    Права участника вытекают из групп, в которых он состоит. Отдельных «скоупов» у токена нет.
  </Step>
</Steps>

<Callout kind="tip" collapsed="false">
  Приглашение ещё не принято? Его можно отозвать через `POST /api/v1/invitations/{id}/revoke`. Принятое приглашение не отзывается - вместо этого участника убирают из групп.
</Callout>

## Проверьте аутентификацию

Самый простой способ проверить токен - запросить список Vault'ов.

<CodeGroup show-lines="true">
  ```bash
  curl -i "[BASE_URL]/api/v1/vaults" \
    -H "Authorization: Bearer $V3_TOKEN"
  ```

  ```javascript
  const res = await fetch("[BASE_URL]/api/v1/vaults", {
    headers: { Authorization: `Bearer ${process.env.V3_TOKEN}` },
  });
  console.log(res.status); // 200 — токен принят
  ```

  ```python
  res = requests.get(
      "[BASE_URL]/api/v1/vaults",
      headers={"Authorization": f"Bearer {os.environ['V3_TOKEN']}"},
  )
  print(res.status_code)  # 200 — токен принят
  ```
</CodeGroup>

Если токен отсутствует или истёк, вернётся `401`:

```json
{
  "error": "Unauthorized",
  "message": "Authentication required. Please provide a valid API token",
  "code": 401
}
```

## Кто что видит

Аутентификация отвечает на вопрос «кто вы», а модель доступа - «что вам можно». В V3 Custody доступ вытекает из членства в группах, а видимость по умолчанию ограничена: обычный участник видит свои адреса, операции и балансы, администратор - весь Vault. Права применяются ещё до расчётов, поэтому чужие данные не попадают даже в агрегаты.
