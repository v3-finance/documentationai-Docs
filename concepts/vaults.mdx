Vault - это отдельное пространство вашей организации в V3 Custody: у него есть код (`code`, slug), имя и, что самое главное, **структура деривации**, которую вы задаёте сами. Почти все маршруты API начинаются с кода Vault'а, а все адреса, балансы, политики и отчёты живут внутри него.

[Введение](/introduction) уже описало Vault в двух словах. Здесь разберём, из чего он собран и как из ваших сегментов получаются детерминированные адреса.

## Схему адресов вы проектируете сами

Обычный кошелёк выдаёт адреса «как получится». Vault идёт от обратного: вы описываете, **какими осями** различаются ваши адреса, а платформа превращает это в дерево путей деривации.

Каждый адрес - это лист дерева. Дорога от корня к листу состоит из сегментов, и каждый сегмент отвечает за одну ось: сеть, назначение, актив, клиент, стадия - набор выбираете вы. Порядок сегментов фиксирован: он и определяет форму пути.

Вот как выглядит дерево на примере. Каждый уровень ниже `network` ветвится по своим вариантам, а лист - это конкретный адрес:

<MermaidDiagram chart={`
flowchart TD
V["Vault · acme-otc"] --> N["network · TRON (coinType 195)"]
N --> P["purpose · invoices | settlement"]
P --> A["asset · usdt | usdc"]
A --> C["client · 0..2^31-1 (динамический)"]
C --> L["адрес-лист · m/44/195/0/0/42"]
`} />

## Сеть - обязательный первый сегмент

В структуре есть один особый сегмент - `network`. Он определяет блокчейн и его `coinType` по стандарту BIP‑44 (например, TRON - 195, Ethereum - 60). Значения сети попадают в глобальный реестр Network, а путь всегда начинается с `m/44/{coinType}/...`.

Один Vault может держать несколько сетей: к нему подключаются нужные `coinType`, и под каждую строится своя ветка.

## Сегменты: статические и динамические

Остальные сегменты - это **Route'ы**, упорядоченные полем `order` (нормализуется от 0). Route бывает двух видов:

- **Статический** - закрытый список вариантов, который вы задаёте заранее. Например, `purpose` = `invoices` | `settlement`, `asset` = `usdt` | `usdc`. Каждый вариант хранит свой индекс в пути; ненужные варианты можно отключить (`disabled`), не ломая уже выданные адреса.
- **Динамический** - не список, а целочисленный индекс в диапазоне `[0, 2^31−1]`. Он даёт новую ветку на каждую сущность: на клиента, на заявку, на депозит. Именно так под каждого клиента заводится отдельное поддерево, а адресов в нём - сколько угодно.

|                  | Статический                 | Динамический                       |
| ---------------- | --------------------------- | ---------------------------------- |
| Что это          | закрытый список вариантов   | целочисленный индекс `[0, 2^31−1]` |
| Примеры          | `purpose`, `asset`, `stage` | `client`, `invoice`, `deposit`     |
| Сколько значений | немного, известны заранее   | сколько угодно, появляются на ходу |
| Роль             | категория                   | экземпляр                          |
| Изменение        | вариант можно `disabled`    | каждый новый индекс - новая ветка  |

<Callout kind="info" collapsed="false">
  Смысл разделения простой: статические сегменты - это ваши **категории** (их немного, они известны заранее), динамические - ваши **экземпляры** (их много, они появляются на ходу).
</Callout>

## Как из сегментов рождается адрес

Адрес создаётся выбором значения для каждого сегмента. Дальше платформа собирает канонический путь и заводит адрес:

<Steps>
  <Step title="Выбираются значения сегментов" icon="list" title-type="p">
    Сеть (`networkCode`) и значения статических сегментов (`staticSegments`). Для динамических сегментов индекс подбирается автоматически.
  </Step>

  <Step title="Считается следующий индекс" icon="hash" title-type="p">
    Для этой комбинации сегментов берётся следующий свободный `pathIndex` (с повтором при конкурентном конфликте) - так два параллельных запроса не займут один путь.
  </Step>

  <Step title="Собирается канонический путь" icon="route" title-type="p">
    Из значений строится путь вида `m/44/{coinType}/{seg0}/{seg1}/...` - по одному числу на сегмент, в фиксированном порядке.
  </Step>

  <Step title="Проверяется политикой" icon="shield" title-type="p">
    Создание адреса проходит через Policy Engine (`action=create_address`): он может разрешить, отклонить или отправить на подтверждение.
  </Step>
</Steps>

Пример создания адреса:

<CodeGroup show-lines="true">
  ```bash
  curl -X POST "[BASE_URL]/api/v1/vaults/demo_vault/addresses" \
    -H "Authorization: Bearer $V3_TOKEN" \
    -H "Content-Type: application/json" \
    -d '{
      "networkCode": "tron_network",
      "staticSegments": { "purpose": "invoices", "asset": "usdt" }
    }'
  ```

  ```javascript
  await fetch("[BASE_URL]/api/v1/vaults/demo_vault/addresses", {
    method: "POST",
    headers: {
      Authorization: `Bearer ${process.env.V3_TOKEN}`,
      "Content-Type": "application/json",
    },
    body: JSON.stringify({
      networkCode: "tron_network",
      staticSegments: { purpose: "invoices", asset: "usdt" },
    }),
  });
  ```

  ```python
  requests.post(
      "[BASE_URL]/api/v1/vaults/demo_vault/addresses",
      headers={"Authorization": f"Bearer {os.environ['V3_TOKEN']}"},
      json={
          "networkCode": "tron_network",
          "staticSegments": {"purpose": "invoices", "asset": "usdt"},
      },
  )
  ```
</CodeGroup>

## Путь читается в обе стороны

Поскольку путь детерминирован, его можно собрать из сегментов и разобрать обратно:

- `POST /api/v1/vaults/{code}/derivation-path/build` - собрать канонический путь из значений сегментов. Проверяет, что сеть подключена к Vault, присутствуют все Route'ы, статические варианты существуют и включены, а динамические значения - целые в допустимом диапазоне.
- `POST /api/v1/vaults/{code}/derivation-path/parse` - разобрать путь обратно на сеть и значение каждого сегмента. Ошибётся, если префикс не `m/44/`, `coinType` не подключён к Vault или число сегментов не совпадает со структурой.

Разберём путь на примере:

```typescript
m / 44 / 195 / 0 / 0 / 42
```

- `44` - стандарт BIP‑44.
- `195` - `network`: TRON (это и есть `coinType`).
- `0` - `purpose`: `invoices` (статический вариант).
- `0` - `asset`: `usdt` (статический вариант).
- `42` - `client`: индекс 42 (динамический сегмент).

### Одна схема - много адресов

Одна и та же схема порождает сколько угодно адресов - меняются лишь значения сегментов:

| purpose    | asset | client | Путь              | Что это                    |
| ---------- | ----- | ------ | ----------------- | -------------------------- |
| invoices   | usdt  | 42     | `m/44/195/0/0/42` | Инвойсы клиента 42, USDT   |
| invoices   | usdt  | 43     | `m/44/195/0/0/43` | Инвойсы клиента 43, USDT   |
| settlement | usdc  | 42     | `m/44/195/1/1/42` | Сеттлмент клиента 42, USDC |

(`purpose`: invoices = 0, settlement = 1; `asset`: usdt = 0, usdc = 1; `client` - индекс.)

## Как проектировать схему

Проектируйте оси заранее - их порядок и состав потом менять тяжело:

- **Идите от учёта и политик.** Сегменты станут осями отчётов и селекторами Policy Engine - выбирайте те, по которым реально будете сворачивать обороты и писать правила.
- **Порядок фиксирован.** Он определяет форму пути; после того как выданы адреса, менять порядок нельзя. Продумайте его сразу.
- **static - категории, dynamic - экземпляры.** Немного известных заранее значений → статический сегмент; много появляющихся на ходу сущностей → динамический.
- **Не пере-сегментируйте.** Каждая ось умножает дерево. Добавляйте только то, по чему будете фильтровать, гейтить или отчитываться.
- **Отключайте, а не удаляйте.** Ненужный статический вариант помечайте `disabled` - уже выданные адреса останутся валидными.
- **Одна сеть — один&#x20;****`coinType`****.** Подключайте нужные сети; под каждую строится своя ветка.

<Callout kind="alert" collapsed="false">
  Порядок и набор Route'ов - это «схема БД» вашего Vault'а. Ошибку в них тяжело исправить задним числом, поэтому спроектируйте оси до создания Vault'а.
</Callout>

## Типовые паттерны

- **Поддерево на клиента.** Динамический `client`: под каждого клиента - своя ветка, адресов в ней сколько угодно.
- **Адрес на инвойс или заказ.** Динамический `invoice` / `order`: каждому счёту - отдельный адрес, чтобы поступления сверялись автоматически.
- **Разделение по назначению или стадии.** Статические `purpose` (`invoices` / `settlement`) или `stage` (`hot` / `cold`) - чтобы писать разные политики и сворачивать отчёты по смыслу.

## Почему дерево - это модель учёта

Форма пути - не техническая деталь, а способ вести учёт:

- **По адресу видно назначение.** `purpose=invoices`, `asset=usdt`, `client=42` - сразу понятно, что это адрес для инвойсов конкретного клиента, а не безымянная строка.
- **Политики пишутся по тем же сегментам.** Policy Engine выбирает правила по сети, активу, назначению - тем же осям, что и дерево. Не нужно перечислять адреса вручную.
- **Отчёты сворачиваются по осям.** Балансы и обороты агрегируются по сети, активу, назначению, клиенту - потому что это уже заложено в структуру.

## Создание Vault

Vault со всей структурой деривации создаётся одним запросом `POST /api/v1/vaults`. В теле передаётся `RouteMap` - карта сегментов, обязательно со спец‑ключом `network` (его варианты добавляются в реестр Network по `coinType`); остальные ключи становятся Route'ами, а их `order` нормализуется от 0 в порядке следования.

Полную конфигурацию созданного Vault'а - подключённые сети (по `coinType`) и Route'ы (по `order`) со всеми вариантами - отдаёт `GET /api/v1/vaults/{code}`.

<Callout kind="alert" collapsed="false">
  Точная схема тела `RouteMap` и всех полей - в [Справочнике API](/api-reference) на странице создания Vault'а. Здесь описан смысл структуры, а не формат запроса.
</Callout>

## Термины

<Expandable title="Словарь деривации" default-open="false">
  - **Route** - сегмент-ось (все, кроме `network`), упорядоченный полем `order`.
  - **Вариант (variant)** - конкретное значение статического Route'а (например, `invoices`).
  - **`pathId`** — индекс варианта статического Route'а в пути.
  - **`pathIndex`** — индекс, который платформа подбирает автоматически для комбинации сегментов при создании адреса.
  - **`coinType`** — идентификатор сети по BIP‑44 (TRON — 195, Ethereum — 60).
</Expandable>
