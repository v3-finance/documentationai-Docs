Когда Policy Engine возвращает `queue`, действие не выполняется сразу - оно превращается в **заявку на подтверждение** и ждёт нужного числа одобрений. На этой странице - как заявка живёт от создания до разрешения. Информацию о том, кто и почему ставит действие в очередь вы найдете на странице [Policy Engine](/concepts/policy-engine).

## Откуда берётся заявка

Действие, меняющее состояние (перевод, удаление адреса, изменение контрагента), возвращает один из двух ответов:

- **`200`** - политика разрешила (`allow`), действие выполнено сразу.
- **`202`** - политика поставила в очередь (`queue`), создана заявка. В ответе - её идентификатор.

Заявка несёт **снапшот решения** на момент создания: какая политика решила (`decisionPolicyId`), кто вправе подтверждать и какой порог. Поэтому поздние правки политики не меняют уже созданные заявки.

## Жизненный цикл

<MermaidDiagram chart={`
flowchart TD
P["PENDING (ждёт голосов)"]
P -->|набран порог approve| A["APPROVED (действие применено)"]
P -->|reject или stale| R["REJECTED"]
P -->|инициатор отменил| C["CANCELLED"]
`} />

| Статус      | Что значит                               | Резерв (для перевода)      |
| ----------- | ---------------------------------------- | -------------------------- |
| `PENDING`   | ждёт голосов                             | держится в `reserved`      |
| `APPROVED`  | набран порог, действие применено         | списывается                |
| `REJECTED`  | вето одобряющего или устаревание (stale) | возвращается в `available` |
| `CANCELLED` | инициатор отменил (перевод - `/cancel`)  | возвращается в `available` |

## Как голосуют (m-of-n)

Голос подаёт член approver-группы заявки. Инициатор не голосует за собственную заявку (если это не разрешено политикой явно), и у каждого - один голос. Например, при пороге **2 из 3** нужно два `approve`; один `reject` - вето, заявка сразу `REJECTED`.

Голосование по заявке:

<CodeGroup show-lines="true">
  ```bash
  curl -X POST "[BASE_URL]/api/v1/vaults/acme-otc/approval-requests/REQUEST_ID/approvals" \
    -H "Authorization: Bearer $V3_TOKEN" \
    -H "Content-Type: application/json" \
    -d '{ "decision": "approve" }'
  ```

  ```javascript
  await fetch("[BASE_URL]/api/v1/vaults/acme-otc/approval-requests/REQUEST_ID/approvals", {
    method: "POST",
    headers: {
      Authorization: `Bearer ${process.env.V3_TOKEN}`,
      "Content-Type": "application/json",
    },
    body: JSON.stringify({ decision: "approve" }),
  });
  ```

  ```python
  requests.post(
      "[BASE_URL]/api/v1/vaults/acme-otc/approval-requests/REQUEST_ID/approvals",
      headers={"Authorization": f"Bearer {os.environ['V3_TOKEN']}"},
      json={"decision": "approve"},
  )
  ```
</CodeGroup>

Финальный `approve`, добравший порог, **применяет целевое действие в этом же запросе**. В ответе - финальный статус и `resolvedResultId` (или `applyError`, если применить не удалось).

Есть две поверхности голосования:

| Поверхность                        | Для чего             | Статус ожидания     |
| ---------------------------------- | -------------------- | ------------------- |
| `approval-requests/{id}/approvals` | любые gated-действия | `PENDING`           |
| `transfers/{id}/approvals`         | только переводы      | `awaiting_approval` |

<Callout kind="alert" collapsed="false">
  `reject` - это вето: одного отклонения достаточно, чтобы заявка стала `REJECTED`. Порог набирается только из `approve`. Имя поля голоса (здесь - `decision`) сверьте со [Справочником API](/api-reference).
</Callout>

## Снапшот и защита от гонок

Два механизма делают исход предсказуемым:

- **Снапшот подписантов.** Заявка помнит одобряющих и порог такими, какими они были в момент создания. Изменили политику после - уже открытые заявки это не затронет.
- **Optimistic-lock.** Финальный `approve` применяет действие атомарно. Если целевой объект успел измениться с момента создания заявки, она помечается `REJECTED` (stale), а не применяет устаревшее действие. Так исключены гонки между параллельными изменениями.

## Композитные заявки

Несколько связанных действий можно оформить как одну заявку с единым флоу одобрения:

- `POST /api/v1/vaults/{code}/approval-requests/composite` - цепочка шагов как единая сущность. Каждый шаг гейтится **своей** политикой; голос `approve` засчитывается тем шагам, где голосующий уполномочен; заявка становится `APPROVED`, когда каждый шаг набрал свой порог. `reject` - вето всей цепочки. Если все шаги разрешены сразу, цепочка применяется без заявки (`applied: true`).

## Где смотреть заявки

- `GET /api/v1/vaults/{code}/approval-requests` - заявки, видимые вам (как инициатору, одобряющему или админу).
- `GET /api/v1/vaults/{code}/approval-requests/{id}` - детали одной заявки.

Фильтры ленты:

| Фильтр                                            | Что фильтрует                                     |
| ------------------------------------------------- | ------------------------------------------------- |
| `status`                                          | `PENDING` / `APPROVED` / `REJECTED` / `CANCELLED` |
| `action`                                          | тип действия                                      |
| `mine=true`                                       | где я инициатор                                   |
| `pendingMine=true`                                | что ждёт моего голоса                             |
| `from` / `to`                                     | окно по времени создания                          |
| `resolvedFrom` / `resolvedTo`                     | окно по времени разрешения                        |
| `initiatorId` / `approverId` / `decisionPolicyId` | по участникам и политике                          |

<Callout kind="tip" collapsed="false">
  `pendingMine=true` отвечает на вопрос «что ждёт именно моего голоса» - удобно для дашборда одобряющего.
</Callout>

## Термины

<Expandable title="Словарь аппрувалов" default-open="false">
  - **Заявка (approval request)** - отложенное действие, ждущее подтверждений.
  - **approver-группа** - кто вправе голосовать по заявке.
  - **`threshold`** - сколько `approve` нужно (m из n).
  - **veto** - один `reject` отклоняет заявку.
  - **stale** - цель изменилась с момента создания → заявка `REJECTED`, действие не применяется.
  - **Композитная заявка** - цепочка шагов, каждый под своей политикой, как единое целое.
  - **`decisionPolicyId`** - политика, которая поставила действие в очередь (в снапшоте заявки).
</Expandable>
